# db_update.py 사용 안내

`complaints.db`의 민원 데이터가 전부 `접수` 상태이거나 처리 이력이 없어서, 시연/발표용으로 **status / updated_at / like_count** 세 컬럼만 현실적인 패턴으로 재생성하는 스크립트입니다.

## 이 폴더에 있는 파일이 각각 뭔지 (제일 먼저 읽어주세요)

작업하면서 파일이 3개 늘었습니다. 각각 뭔지 헷갈리지 않게 정리합니다.

| 파일명 | 뭔지 | 지금 써도 되는 파일인지 |
| --- | --- | --- |
| **`complaints.db`** | 지금 실제로 앱이 읽고 쓰는 **현재 DB**. `db_update.py`를 한 번 실행해서 status/updated_at/like_count가 이미 시연용으로 바뀐 최신 상태. | ✅ 이게 실제 사용 파일. 서버 켤 때 이걸 봄. |
| **`complaints_backup_before_update.db`** | `db_update.py`를 실행하기 **직전**의 원본을 그대로 복사해둔 백업 파일. 앱이 참조하지 않는, 만약을 위한 안전망용 파일. | ❌ 앱에서 안 씀. 혹시 데이터가 이상해졌을 때 되돌리는 용도로만 보관. |
| **`db_update.py`** | `complaints.db`의 status/updated_at/like_count를 카테고리별 규칙에 맞춰 랜덤으로 다시 채워주는 **실행 스크립트**. 이미 한 번 실행 완료된 상태라 다시 실행할 필요 없음. | ⚠️ 재실행 금지 (이미 반영됨). 나중에 데이터를 통째로 다시 만들어야 할 때만 사용. |

**한 줄 요약**: `complaints.db`만 보시면 되고, 나머지 둘은 "왜 이렇게 됐는지"와 "문제 생기면 되돌리는 법"을 위한 참고용 파일입니다.

## 무엇을 바꾸고, 무엇을 안 바꾸는가

| 구분 | 대상 |
| --- | --- |
| **변경** | `complaints.status`, `complaints.updated_at`, `complaints.like_count` |
| **변경 안 함** | `id`, `user_id`, `category`, `raw_content`, `summary`, `photo_url`, `created_at` |
| **변경 안 함** | `users` 테이블, `complaints_likes` 테이블 전체 |

즉 민원 원문·작성자·작성일 같은 원본 데이터는 그대로 두고, "운영진이 얼마나 처리했는지"를 보여주는 부분만 그럴듯하게 채워 넣는 스크립트입니다.

## ⚠️ 지금 당장 실행하실 필요 없습니다

**이 스크립트는 이미 1회 실행 완료됐고, 그 결과가 지금 `complaints.db`에 반영되어 있습니다.**
지금 폴더를 받으신 분은 그냥 `complaints.db`를 그대로 쓰시면 됩니다. `db_update.py`를 또 실행하시면 이미 배정된 status/updated_at/like_count가 **또 랜덤으로 덮어써져서, 지금 확인한 시연용 데이터와 달라집니다.**

## 나중에 다시 실행해야 할 경우에만 (예: 원본 민원 데이터가 새로 추가/변경돼서 다시 생성해야 할 때)

아래는 "지금 하라"는 게 아니라, 앞으로 필요할 때를 위한 안내입니다.

```powershell
# 프로젝트 루트에서 (complaints.db와 같은 위치에서 실행 시)
python db_update.py --db complaints.db

# 다른 경로에 있을 경우
python db_update.py --db data/complaints.db
```

실행 전 체크리스트:
- [ ] uvicorn 등 DB 파일을 물고 있는 서버가 켜져 있다면 **먼저 종료**
- [ ] 정말 다시 생성해야 하는 상황이 맞는지 한 번 더 확인 (지금 데이터로 충분하면 실행하지 말 것)
- [ ] 실행은 1회만 — 두 번 실행하면 방금 배정한 값을 또 덮어씀

## 실행하면 자동으로 생기는 것

- `complaints_backup_before_update.db` — 실행 직전 원본 백업. 문제가 생기면 이 파일로 되돌리면 됨
  ```powershell
  Copy-Item complaints_backup_before_update.db complaints.db -Force
  ```

## 로직 요약

### 1. status 배정
- **최근 20건** (`created_at` 기준 최신순 20개): `접수`를 포함한 4개 상태 중 카테고리별 가중치로 랜덤 배정
- **나머지 81건**: `접수` 제외, `처리중 / 완료 / 거절` 3개 중 랜덤 배정
  - → "예전 민원인데 아직도 접수 상태로 방치"되는 비현실적인 상황 방지

### 2. 카테고리별 상태 가중치 (%)

| 카테고리 | 접수 | 처리중 | 완료 | 거절 | 의도 |
| --- | --- | --- | --- | --- | --- |
| 시설/환경 | 15 | 40 | 30 | 15 | 물리적 조치 필요 → 처리중 체류 김 |
| 학습 장비 | 15 | 40 | 35 | 10 | 대부분 조치되고 거절은 적음 |
| 수업/학습 | 25 | 20 | 30 | 25 | 판단 필요 → 완료/거절 반반 |
| 청결 | 20 | 15 | 55 | 10 | 즉각 조치 가능 → 완료 압도적 |
| 개선 방안 | 20 | 15 | 25 | 40 | 건의사항 특성상 미채택(거절) 많음 |
| 비공개 - 기타 | 25 | 30 | 25 | 20 | 고르게 분산 |

### 3. 처리 소요일 (`updated_at - created_at`)

| 상태 | 기본 범위 |
| --- | --- |
| 접수 | 0일 (아직 미처리) |
| 처리중 | 1~5일 |
| 완료 | 3~12일 |
| 거절 | 1~4일 |

카테고리 보정:
- 시설/환경, 학습 장비: **+2~3일** (물리적 조치라 오래 걸림)
- 청결: **-1~2일** (빠른 조치)
- 개선 방안: **+2일** (검토 시간 필요)
- 수업/학습, 비공개-기타: 보정 없음

추가로 계산된 `updated_at`이 토/일요일에 걸리면 다음 평일로 이동시킴 (운영진 휴무 반영). 또한 **스크립트 실행 시점의 오늘 날짜**를 넘지 않도록 상한 처리함 (하드코딩된 날짜 아님 → 언제 실행해도 자동으로 오늘까지만 반영).

### 4. 공감 수 (`like_count`)
- 비공개-기타: 0~2 사이 랜덤 (심심한 사람이 누른 정도)
- 그 외 카테고리: 카테고리별 상한(시설/환경·학습 장비 8, 개선 방안 10, 수업/학습·청결 5) 안에서 상태별로 차등
  - 처리중 상태가 가장 높은 구간 (오래 미해결일수록 공감 쌓임)
  - 완료·거절은 중간~낮은 구간

### 5. 재현성
`random.seed(42)` 로 고정 — 데이터 재생성이 필요할 때 몇 번을 실행해도 동일한 분포가 나옵니다. (단, `updated_at`의 상한은 "실행 시점의 오늘 날짜" 기준이라 실행일이 다르면 캡 값 자체는 달라질 수 있음. status/like_count/소요일 분포 로직 자체는 항상 동일)

## 알려진 제약사항 (그대로 둔 것)

- `complaints_likes` 테이블은 건드리지 않아서, 새로 생성된 `like_count`와 실제 공감 이력 row 수가 서로 정합하지 않습니다. 화면 조회 위주의 시연에는 문제없으나, 실시간으로 "공감하기" 버튼을 눌러 카운트 증가를 보여줄 계획이면 참고하세요.
- `photo_url`은 이번 작업 범위에서 제외했습니다 (원본 값 그대로 유지, 신규 추가 없음).
